# Java Development｜花店系统持续开发

## 目标与边界

为 Spring Boot 后端提供持续开发指导，覆盖商品、分类、库存、采购、销售订单、经营收支、用户权限和报表等业务。先尊重仓库现状，再做最小、可验证的修改。

- 仅处理 Java/Spring Boot 后端及其构建、测试、配置、数据库访问相关内容。
- 不负责需求完整性与产品规格（交给 `spec-writer`）、数据库整体建模（交给 `database-schema-designer`）、项目初始骨架（交给 `spring-scaffold`）、Vue UI/视觉（交给前端 Skills）。
- 不因 Skill 存在就强制采用某个 Java 版本、Spring Boot 大版本、Maven/Gradle、MyBatis/JPA、Lombok 或数据库。
- 若仓库已有实现、配置、依赖和约定，现状优先。未选定数据库时，不生成假定特定数据库的最终 DDL 或驱动配置。

## 工作流程

1. **识别项目**：检查 README、构建文件（pom.xml/build.gradle）、Java 版本、Spring Boot 版本、包结构、持久层、迁移方案、测试框架和现有代码风格。
2. **确认需求**：找到关联规格与验收条件。若业务规则会影响库存、金额、收支归属、退款或订单状态且尚未定义，先提出一个简短问题，不自行编造。
3. **划定范围**：列出要修改的文件、接口、数据表/迁移、影响的业务流程和潜在兼容风险。只改完成任务所需的最小范围。
4. **实现后端**：沿用项目已有分层和模式；校验放在服务端；对有副作用的业务操作明确事务边界；金额使用合适的十进制定点类型，不用浮点数计算货币。
5. **验证**：运行与改动相称的格式检查、编译、单元测试和集成测试。若未执行，明确说明原因，不得声称通过。
6. **交付说明**：简述改动、业务影响、执行过的验证、未验证事项及可复现命令。

## 花店系统关键约束

- 将业主投入、个人取款、借款、还款、经营收入和经营费用作为不同业务概念处理；不得混为销售收入或经营费用。
- 库存变更应有明确来源和业务记录。采购入库、销售出库、退货、盘点调整不可无记录地直接覆盖库存数量。
- 创建订单、扣减库存、计算订单金额等多步骤操作应评估事务一致性；防止重复提交导致重复订单或重复扣减。
- 订单状态变更必须有明确允许的状态流转；不允许仅通过前端控制业务合法性。
- 价格、折扣、数量、库存和金额由服务端校验；接口不得信任客户端传入的汇总金额。
- 设计审计/操作记录时，仅记录业务所需信息；不记录密码、令牌或不必要的敏感数据。
- 在数据库尚未确定前，使用数据库中立的业务模型描述；选定数据库后再确定具体类型、索引、约束和迁移脚本。

## Java/Spring Boot 实施规则

- 依赖注入优先沿用项目现有方式；不擅自引入 Lombok 或新的框架。
- Controller 负责 HTTP 输入输出与参数校验边界；业务规则放在合适的业务服务层；持久层遵循现有模式，不为简单 CRUD 过度分层。
- 对外接口保持一致的响应和错误语义；避免把堆栈、SQL、内部路径或密钥返回给客户端。
- 异常不能被静默吞掉；保留有诊断价值的原因链，日志不泄露凭据。
- 修改配置时区分开发/测试/生产环境；密钥从安全配置注入，不硬编码进仓库。
- 不进行无关的大规模重构，不批量升级依赖，不更改公共 API 或数据结构而不说明兼容影响。
- 不确定是否可破坏兼容性时，优先向后兼容，并先说明迁移影响。

## 测试要求

根据改动选择最小充分测试组合：

- 纯业务计算/状态流转：单元测试，覆盖正常、边界和异常输入。
- Controller 参数校验与响应：Web 层测试。
- 数据访问、事务、库存与订单一致性：集成测试；使用项目已采用的测试数据库方案。
- 影响端到端业务流程的改动：建议通过 `playwright-e2e-testing` 验证前后端流程，但本 Skill 不代替该 Skill。
- 涉及权限、SQL、输入验证、敏感配置时，额外检查越权、注入和信息泄露风险。

## 何时需要其他 Skill

- 需求不清楚或验收标准缺失：先用 `spec-writer`。
- 表结构、关系、索引或迁移策略需要整体设计：用 `database-schema-designer`。
- 初始化项目：用 `spring-scaffold`，并在初始化后由本 Skill 审查后端代码。
- Vue 页面或交互：用 `frontend-design`；原型与页面清单用 `frontend-ui-prototype`。
- 需要评估已有代码整体风险：用 `safe-refactor`（重构）或适用的审查 Skill。
- 需要浏览器端完整流程测试：用 `playwright-e2e-testing`。
- 方案复杂度有争议：用 `anti-over-engineering`。

## 输出格式

对于非平凡任务，输出：
1. **理解与范围**：目标、受影响模块、假设。
2. **实施变更**：关键文件与业务逻辑。
3. **验证结果**：真实执行的命令和结果。
4. **风险与后续**：未验证事项、迁移/兼容风险及下一步。

不得虚构运行结果、数据库选择、业务规则或已执行的测试。
